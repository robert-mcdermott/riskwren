# Content packs

RiskWren ships its content as **packs**: data files that are loaded into the database, versioned, and replaceable. A whole program configuration, a library of risks or controls, a framework, and a questionnaire are all packs. A revised scale, a new framework version, or another organization's way of working arrives as a pack update, never as a code change.

This document defines the pack format, the rules for what text may be shipped, the packs planned, and where their content comes from.

## Kinds of pack

| Kind | Holds | Loaded into |
|---|---|---|
| **Program** | Vocabularies, the risk taxonomy with appetite, the scoring method, cadences, the authority table, severity clocks | Program settings, `risk_category`, `scoring_method` |
| **Risk library** | Reusable risk statements by category, each suggesting controls | `risk_library` |
| **Control library** | Controls with statements, objectives, kind, nature, and frequency, and crosswalks to framework requirement codes | `control`, `control_requirement` |
| **Framework** | A tree of requirements with stable codes, and optional baselines | `framework`, `requirement`, `baseline` |
| **Questionnaire** (wave 3) | Sections and questions with conditions and scoring | `questionnaire` |

## Format

A pack is one JSON document. JSON is chosen because the standard library reads and writes it, it diffs well enough in review, and it needs no parser dependency.

```json
{
  "pack": {
    "key": "nist-csf",
    "kind": "framework",
    "framework_kind": "standard",
    "title": "NIST Cybersecurity Framework",
    "version": "2.0",
    "pack_version": "1.0.0",
    "publisher": "National Institute of Standards and Technology",
    "source_url": "https://www.nist.gov/cyberframework",
    "built_from": "…",
    "license": "Public domain (a work of the United States government)",
    "text_policy": "verbatim",
    "attribution": "…"
  },
  "requirements": [
    { "code": "GV", "title": "Govern", "kind": "function", "group": true, "children": [
      { "code": "GV.OC", "title": "Organizational Context", "group": true, "children": [
        { "code": "GV.OC-01", "text": "…", "guidance": "…" }
      ]}
    ]}
  ],
  "baselines": [
    { "key": "low", "title": "Low-impact baseline", "codes": ["AC-1", "AC-2"] }
  ]
}
```

- `framework_kind` is standard, regulation, agreement, or internal.
- A requirement has a `code`, and any of a `title`, its `text`, the source's `guidance`, a `kind` (the source's own word for it: control, enhancement, standard), and `children`. One marked `group` is a heading: it holds others and is not itself something to meet or to map a control to.
- A baseline is a published selection: a key, a title, and the codes it selects.
- `built_from` names the publisher's file the pack was generated from.
- `version` is the version of the source document; `pack_version` is the version of this pack, which also changes when mappings or wording are corrected.
- Every requirement has a `code` that is stable across pack versions. Codes are how crosswalks, implementations, tests, and evidence stay attached when a pack is updated.
- A pack is checked whole before anything is written. A pack with anything wrong is refused whole, with every problem listed: a code used twice, a baseline naming a code that is not there, a field that is not known, text the pack's policy does not allow.

Built-in packs live in `src/riskwren/resources/packs/`. Each is generated by a script in `scripts/` from the publisher's own machine-readable file where one exists, so that a pack can be rebuilt and compared when its source is revised; the script records the source file and its version in the pack. An organization can load its own packs from a file.

## What text may be shipped

RiskWren is Apache 2.0 licensed, and nothing in the repository may compromise that. Source documents come under very different terms, so every pack declares a **text policy**, and the policy decides what the pack may contain.

| Text policy | Applies to | What the pack contains |
|---|---|---|
| `verbatim` | Public-domain works and works dedicated to the public domain: United States government publications, the text of laws and regulations | Codes, titles, and the source text itself |
| `attributed` | Works under attribution licenses that permit adaptation | Codes, titles, and text, with the required attribution shown wherever the content appears in the app and in every export |
| `identifiers` | Copyrighted standards and guidance with no open license | Only the codes, and RiskWren's own short, plain-language label for what each requirement is about. Never the source's titles or wording |
| `summary` | Public-domain works where RiskWren carries its own short summary because it is easier to act on | Codes, titles, and a one-sentence summary written for RiskWren |

Works whose licenses forbid adaptation, forbid use inside a product, or require a paid license for tool providers are **not shipped at all**, even as identifiers, unless their publisher's terms clearly allow it. RiskWren instead provides the means to load them: an organization that holds a license creates or imports the framework itself.

For an `identifiers` pack, an organization that holds a license to the source can **import the official text locally**. Imported text is marked as licensed, is shown only inside that installation, and is excluded from every pack export.

A framework the organization enters for itself has the policy `own`: its text is the organization's to hold, and it never ships.

The policy is enforced in two places: a test checks every built-in pack against its declared policy (an `identifiers` pack with long text fields fails the build), and each pack's publisher, license, and attribution are displayed on the framework's page in the app.

## Planned packs

### With wave 1: the default program

A complete, working program so that a new installation can record and rate risks on its first day:

- **Vocabularies:** criticality, data classes (Public, Internal, Confidential, Restricted, each with a definition and examples), process, system, and third-party kinds, hosting, lifecycle, control kinds, natures, and frequencies, owner capacities, link kinds, and unit kinds.
- **Risk taxonomy:** nine top-level categories with subcategories, each top-level category with a default appetite: Strategic · Research and scientific integrity · Clinical and participant safety · Regulatory and legal · Information and technology · Operations and facilities · People and culture · Financial and stewardship · Third party.
- **Scoring method:** the default five-by-five method in [engine.md](engine.md), with definitions for every level of every dimension.
- **Cadences, the authority table, and severity clocks** as described in the engine.

It is written for a research and health organization and is meant to be edited.

### With wave 1: starter libraries

- **Risk library:** about sixty risk statements across the taxonomy, written for RiskWren, each with a cause, an event, a consequence, and suggested starter controls.
- **Starter controls:** about fifty common controls in plain words, each a sentence a control owner would recognize as their own job: *"Access to systems is removed on the day a person leaves."* Written for RiskWren and Apache 2.0 licensed. From wave 2 each carries a crosswalk to the built-in frameworks.

### With wave 2: built-in frameworks

All of the following are works of the United States government, in the public domain, and are shipped `verbatim`. Versions are those current when the pack was built; the pack records its source.

| Pack | Source | Size | Built from |
|---|---|---|---|
| `nist-csf` | NIST Cybersecurity Framework 2.0 | 6 functions, 22 categories, 106 subcategories | The publisher's machine-readable catalog |
| `nist-800-53` | NIST SP 800-53 Rev. 5, release 5.2.0, with the Low, Moderate, High, and Privacy baselines of SP 800-53B | 20 families, about 1,000 active controls and enhancements | The publisher's machine-readable catalog and baseline profiles |
| `nist-800-171` | NIST SP 800-171 Rev. 3 | 17 families, 97 requirements | The publisher's machine-readable catalog |
| `hipaa-security` | HIPAA Security Rule, 45 CFR Part 164 Subpart C | 22 standards and their implementation specifications | The electronic Code of Federal Regulations |

Each loads with one command and arrives with a crosswalk from the starter controls. Where the publisher provides a mapping between two of these (for example from the Security Rule to the Cybersecurity Framework and SP 800-53), it is carried in the pack and used to suggest crosswalks.

SP 800-53 is large. It loads as a catalog; a scope adopts a **baseline** from it, and only that selection is ever put in front of people.

### Never shipped

Frameworks whose terms forbid redistribution or use inside a product. RiskWren supports them the same way it supports a grant's terms or a data use agreement: the organization that holds the right to use them loads them as a framework of its own.

## The organization's own frameworks

Much of what a research or health organization must comply with is not a published standard. It is the terms of an award, a data use agreement, a sponsor's contract, a repository's security requirements, an accreditor's standards, or its own internal policy.

Any of these is entered as a framework of `kind` *agreement* or *internal*: a list of requirements with codes, typed in or imported from a spreadsheet. From then on it behaves exactly like a built-in one: crosswalks, scopes, applicability, readiness, and issues. From wave 4, an **agreement** record adds the dates, the parties, and what the agreement covers.

## Open assessment formats

The Open Security Controls Assessment Language (OSCAL) is the public, machine-readable format used across United States federal security programs. RiskWren treats it as its interchange format for compliance content:

- **In (wave 2, at build time; wave 6, in the app):** catalogs and profiles, which become framework packs and baselines.
- **Out (wave 6):** a scope's control implementations as a system security plan, an assessment's tests as assessment results, and a scope's open issues as a plan of action and milestones.

Because the built-in packs are generated from the publisher's own OSCAL files, a new release of a source catalog is a rebuild and a comparison, not a retyping.

## Updating a pack

Loading a newer version of a framework never alters the old one (wave 4). The app shows what was added, changed, and withdrawn, by code; which controls are mapped to a changed requirement; and which scopes are affected. A scope moves to the new version when its owner says so, and until then its readiness is reported against the version it adopted.

## Rules for writing content

- **Plain words.** A control statement is one sentence saying who does what, how often. A risk statement names a cause, an event, and a consequence.
- **Generic.** No real organization, person, product, or vendor is named. Examples use the demo organization.
- **Original.** Text written for RiskWren is written from scratch, not paraphrased from a copyrighted source.
- **Sourced.** Every framework pack names its publisher, its version, its license, and where it came from.
